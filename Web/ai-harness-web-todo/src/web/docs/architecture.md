# web Architecture

## Boundaries

- HTML 표현(`Todo.Web.View`)과 도메인 타입을 분리합니다. 도메인 구조 변경이 곧바로 화면 파손이 되지 않게 하기 위함입니다.
- 뷰는 규칙을 판단하지 않고 표시만 합니다. 무엇을 보여줄지는 `Todo.Core.Filter`와 `Todo.Core.Status`가 정합니다.
- 설정 해석은 `Todo.Web.Config`가 순수 함수로 담당하고, 환경 변수를 읽는 일은 실행 파일이 합니다.
- 수신 주소는 루프백으로 고정합니다. 인증이 없는 표면에서 접근 경로 제한은 설정이 아니라 경계입니다.
- 다른 어댑터를 거치지 않습니다. `api`를 HTTP로 호출하지 않고 `Todo.Core.UseCase`를 직접 사용합니다.

## 왜 세 번째 어댑터인가

`web`이 `api`를 호출하면 사용자가 프로세스를 둘 띄워야 하고 실패 방식이 두 배가 됩니다. `ARCHITECTURE.md`의 의존 규칙 5도 어댑터 간 참조를 금지합니다.

`PROD-INV-003`을 지탱하는 것은 API 재사용이 아니라 `Todo.Core.UseCase` 공유입니다. 세 표면이 같은 유스케이스를 호출한다는 사실은 `../../../scripts/quality/architecture-check.sh`가 의존 방향으로 검사합니다.

근거 전체는 `../../../docs/decisions/ADR-0004-web-surface.md`에 있습니다.

## 왜 서버 렌더링인가

JavaScript 빌드 툴체인을 도입하면 그 비용이 저장소 전체에 퍼집니다. `lint.sh`, `test.sh`, CI, 완료 정의가 모두 fourmolu와 cabal을 전제로 쓰여 있습니다.

브라우저가 다른 출처로 요청을 보내지 않으므로 CORS를 열 일도 없습니다. CORS를 열면 사용자가 방문한 임의의 페이지가 루프백 서버에 요청을 보낼 수 있게 됩니다.

## 왜 라우트를 타입으로 고정하지 않는가

`api`는 Servant로 라우트를 타입 수준에 두고, 핸들러가 어긋나면 컴파일이 실패합니다. 그 값어치는 라우트가 스크립트가 의존하는 공개 계약이기 때문에 생깁니다(`../../../docs/decisions/ADR-0003-api-boundary.md`).

이 표면의 주소는 계약이 아닙니다. 소비자는 사람의 브라우저뿐이고 버전이나 폐기 정책이 없습니다. 그래서 `Todo.Web.Route`가 경로와 질의를 값 수준에서 해석합니다.

대신 그 해석을 순수 함수로 두어 테스트가 대체하게 했습니다. `parseRoute`는 WAI 요청이 아니라 경로 조각과 질의 쌍을 받으므로 `IO` 없이 검증됩니다. 타입 검사가 주지 않는 보장을 테스트가 줍니다.

이 선택을 뒤집어야 하는 시점은 화면 주소를 외부가 참조하기 시작할 때입니다. 북마크는 해당하지 않지만, 다른 도구가 URL을 조립하기 시작하면 그것은 계약이며 `ADR-0003`의 논리가 적용됩니다.

## 흐름

```text
Request
  |
  v
Todo.Web.Route         경로와 질의 해석, 조건 생성
  |
  v
Todo.Web.Server        유스케이스 호출
  |
  +--> Todo.Core.UseCase --> Todo.Store.Sqlite
  |         (Todo.Core.Filter가 조건을 평가하고 정렬)
  |
  v
Todo.Web.View          HTML. 다시 거르거나 정렬하지 않음
```

## 변경 요청의 방어

이 표면에는 세션이 없습니다. 쿠키가 없으므로 브라우저의 `SameSite` 방어가 적용되지 않고, CSRF 토큰은 서버가 상태를 들고 있어야 하므로 쓰지 않습니다.

폼 제출은 CORS의 제약을 받지 않는다는 점이 문제의 핵심입니다. 사용자가 방문한 임의의 페이지가 루프백 주소로 폼을 보낼 수 있고, 인증이 없으므로 그 요청은 그대로 성공합니다.

`Sec-Fetch-Site`를 확인합니다. 브라우저가 붙이고 페이지 스크립트가 위조할 수 없으며 서버에 상태를 남기지 않습니다. `same-origin`만 허용하고 헤더가 없는 요청도 거부합니다.

적용 범위는 `Todo.Web.Route.isWriteRoute` 하나가 정합니다. 새 변경 경로를 추가하면서 그 함수에 넣지 않으면 확인 없이 통과하므로, `../tests/Todo/Web/RouteSpec.hs`가 모든 생성자를 나열해 분류를 고정합니다.

## 변경 후 되돌려 보내기

변경에 성공하면 303으로 다시 보냅니다. 새로 고침이 같은 변경을 다시 실행하지 않게 하기 위한 것입니다. 삭제 후에는 돌아갈 상세 화면이 없으므로 목록으로 보냅니다.

`PUT`과 `DELETE`를 쓰지 않고 모두 `POST`인 이유는 HTML 폼이 두 메서드를 보낼 수 없기 때문입니다. 숨은 필드로 메서드를 위장하는 방법은 쓰지 않습니다. 경로에 동작을 적는 편이 읽기 쉽고, 이 표면의 주소는 계약이 아닙니다.

## 삭제

삭제는 `GET /todos/{id}/delete`의 확인 화면을 거쳐야 실행됩니다. 상세 화면에는 확인 화면으로 가는 링크만 있고 삭제 폼이 없습니다. 되돌릴 수 없는 동작을 클릭 한 번에 두지 않기 위해서입니다(`../../../docs/product/invariants.md`의 `PROD-INV-001`).

확인 화면은 보관이라는 대안을 함께 알립니다. 두 동작을 혼동하지 않게 하는 것이 제품의 핵심 어휘 결정입니다(`../../../docs/product/terminology.md`).

## 본문 상한

폼 본문은 64 KiB로 제한하고 넘으면 413으로 거부합니다. 이 표면의 폼은 제목과 태그 몇 개가 전부이며, 같은 기계의 다른 프로세스가 큰 본문으로 메모리를 소모하는 것을 막기 위한 것입니다.

## 현재 상태

이 패키지를 도입한 계획과 결과는 `../../../docs/plans/completed/PLAN-2026-08-23-local-web-surface.md`에 있습니다.

| 모듈 | 책임 |

## 화면 주소

| 주소 | 의미 |
|---|---|
| `/` 또는 `/todos` | 목록. 기본은 끝나지 않은 할 일만 |
| `/?all` | 상태를 제한하지 않는 목록 |
| `/?status=<이름>` | 그 상태만. 이름은 `pending`, `in_progress`, `done`, `archived` |
| `/?tag=<태그>` | 태그로 거릅니다. 여러 번 지정하면 모두 가진 할 일만 |
| `/?list=<목록>` | 목록으로 거릅니다 |
| `/todos/<번호>` | 상세 |
| `/todos/<번호>/delete` | 삭제 확인. 조회이며 삭제하지 않습니다 |

질의 조건은 논리곱으로 결합합니다. `api`의 `GET /todos`와 같은 의미이며, 두 표면 모두 `Todo.Core.Filter`가 평가하기 때문입니다.

변경은 모두 `POST`이며 출처 확인을 거칩니다.

| 주소 | 의미 |
|---|---|
| `POST /todos` | 만듭니다 |
| `POST /todos/<번호>/edit` | 내용을 부분 수정합니다. 상태는 바꾸지 않습니다 |
| `POST /todos/<번호>/status` | 상태를 바꿉니다 |
| `POST /todos/<번호>/delete` | 영구 삭제합니다 |

수정에서 마감일 입력을 비운 채 저장하면 마감일이 지워집니다. HTML 폼은 빈 값도 필드를 보내므로 화면에서 날짜를 비우는 것이 곧 제거 요청입니다. 계약의 `PATCH`가 구분하는 세 경우와 같은 의미입니다.
