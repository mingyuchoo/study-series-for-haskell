# Security Tests

입력 검증, 오류 노출 범위와 주요 공격 표면을 검증합니다.

실행 위치: `../../src/api/tests`, `../../src/web/tests`

## 전제

이 앱에는 인증이 없습니다. 네트워크를 여는 두 표면은 `127.0.0.1`에만 바인딩하며, 접근 경로 제한이 유일한 방어선입니다. 근거는 `../../docs/decisions/ADR-0004-web-surface.md`와 `../../docs/product/vision.md`의 비목표에 있습니다.

따라서 여기서 검증하는 것은 인가가 아니라 다음 세 가지입니다.

1. 신뢰할 수 없는 입력이 검증을 통과하지 못하고 저장 계층에 도달하지 않는다.
2. 오류 응답이 저장 경로, SQL, 내부 구조를 노출하지 않는다.
3. 브라우저 표면에서 다른 사이트가 보낸 변경 요청이 처리되지 않는다.

세 번째 항목이 `web`에만 해당하는 이유는 그 표면만 브라우저가 자동으로 요청을 보낼 수 있는 형태이기 때문입니다. `api`는 JSON 본문을 요구하므로 폼 제출로 도달할 수 없고, `cli`에는 원격 호출 경로가 없습니다.

## 다루는 것

- 빈 제목, 과도한 길이, 허용되지 않은 태그 문자
- 인식할 수 없는 상태와 우선순위 값
- 잘못된 JSON 본문과 경로 매개변수
- 사용자 입력에 든 SQL 조각이 값으로만 다루어지는지
- 사용자 입력이 HTML에 이스케이프되어 나타나는지 (`web`)
- 상태를 바꾸는 요청이 `Sec-Fetch-Site: same-origin`일 때만 처리되는지 (`web`)
- 거부 안내가 요청자가 보낸 값을 화면에 되돌려 주지 않는지 (`web`)

## 다루지 않는 것

같은 기계의 다른 프로세스로부터의 방어는 다루지 않습니다. 루프백 바인딩이 막는 것은 네트워크 노출이며, 이미 사용자의 기계에서 실행 중인 프로그램은 데이터베이스 파일을 직접 열 수도 있습니다.

인증이나 다중 사용자 개념을 도입하는 변경은 Level 3이며 이 문서의 전제부터 다시 씁니다.
