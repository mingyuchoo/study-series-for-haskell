# Active Technical Debt

| ID | 영역 | 문제와 영향 | 임시 대응 | 소유자 | 목표 시점 | 제거 조건 |
|---|---|---|---|---|---|---|
| TD-001 | store | 마이그레이션이 `CREATE TABLE IF NOT EXISTS`와 수동 `schema_version` 기록뿐입니다. 열 추가는 재적용으로 처리되지만 변경과 제거를 표현할 수 없고 되돌리는 경로가 없습니다. | 현재 스키마 버전이 1이며 아직 변경이 없습니다. 파괴적 변경을 Level 3으로 묶어 사람의 승인을 요구합니다. | store 담당 | 두 번째 스키마 변경이 필요해질 때 | 버전별 up 스크립트와 적용 이력, 실패 시 동작이 정의되고 테스트로 검증될 때 |
| TD-002 | cli | 통합 수준 테스트가 없습니다. 옵션 파싱과 출력 형식은 검증되지만 명령이 실제 저장소를 거쳐 종료 코드까지 도달하는 경로는 수동 확인에 의존합니다. | `core`와 `store`가 각각 검증되어 있어 조합 실패 가능성이 낮습니다. | cli 담당 | 명령이 다섯 개를 더 늘어날 때 | 임시 데이터베이스에 실행 파일을 실행하고 종료 코드와 출력을 검증하는 테스트가 생길 때 |
| TD-003 | core, api, web | 낙관적 동시성 제어가 없습니다. 두 곳에서 같은 할 일을 읽고 각자 수정하면 나중 쓰기가 앞선 변경을 조용히 덮습니다. 사용자는 자기 수정이 사라진 것을 알 수 없습니다. | CLI 단독 사용에서는 도달하기 어려웠습니다. `web`이 생기면서 탭 두 개로 재현 가능해졌습니다. 개인 사용 규모에서 빈도가 낮다고 보고 받아들였습니다. | core 담당 | 사용자가 변경이 사라지는 것을 실제로 겪을 때, 또는 `TODO-API-v1`을 다음에 바꿀 때 | `updatedAt` 기반 조건부 갱신이 도입되고, 충돌 시 덮어쓰지 않고 알리는 동작이 세 표면에서 검증될 때 |

새 우회책을 추가할 때는 관련 ADR, 사고 또는 계획을 연결하고 제거 조건을 명시합니다. 제거 조건이 없는 항목은 부채가 아니라 방치입니다.
