# ADR-0004: 브라우저 표면과 루프백 제약

- 상태: Accepted
- 날짜: 2026-08-23
- 결정자: Todo Maintainers
- 관련 이슈: `../plans/completed/PLAN-2026-08-23-local-web-surface.md`
- 대체 관계: 없음

## Context

지금까지 이 제품은 명령줄과 HTTP API 두 표면을 제공했고, 그래픽 사용자 인터페이스는 `../product/vision.md`의 비목표였습니다.

사용자가 브라우저에서 할 일을 다루고 싶다고 요청했습니다. 요청의 실제 내용은 "GUI를 원한다"보다 좁습니다. 할 일 하나를 넣을 때는 CLI가 빠르지만, 쌓인 목록을 훑고 우선순위를 다시 잡을 때는 한 줄씩 스크롤하는 터미널이 불편합니다. 필요한 것은 같은 기계에서 목록을 넓게 보는 화면입니다.

비목표를 다시 읽으면 GUI가 왜 거기 있었는지가 드러납니다. GUI는 대개 호스팅, 계정, 기기 간 동기화를 함께 데려옵니다. 그 셋은 이 제품이 거부하는 것이 맞습니다. 하지만 GUI 자체가 그 셋을 필연으로 요구하지는 않습니다. 이 ADR은 그 분리가 실제로 가능한지, 가능하다면 무엇으로 지탱하는지를 결정합니다.

동시에 이미 존재하는 문제 하나가 이 결정에 묶여 있습니다. `TODO-API-v1` 계약은 API가 "신뢰할 수 있는 로컬 환경에서만 실행하는 것을 전제한다"고 쓰지만, `../../src/api/app/Main.hs`는 Warp의 `run`을 사용해 모든 인터페이스에 바인딩합니다. 전제가 코드로 강제되지 않습니다.

## Decision Drivers

- 사용자 데이터가 로컬 파일 밖으로 나가지 않아야 합니다 (`../product/invariants.md`의 `PROD-INV-005`).
- 인증이 없는 상태를 유지하려면 접근 경로가 물리적으로 제한되어야 합니다.
- 모든 표면이 같은 답을 주어야 합니다 (`PROD-INV-003`). 규칙 복제가 구조적으로 어려워야 합니다.
- 기여자가 배워야 할 도구 수가 늘지 않아야 합니다. 저장소는 단일 Haskell 툴체인입니다.
- 화면 때문에 공개 JSON 계약이 흔들리지 않아야 합니다.

## Considered Options

1. 서버 렌더링 HTML 어댑터를 새 패키지 `web`으로 추가하고 루프백에만 바인딩
2. 정적 SPA를 만들고 `api`가 `Raw` 라우트로 함께 서빙
3. 정적 SPA를 별도 출처에서 띄우고 `api`에 CORS 허용
4. `web`이 `api`를 HTTP로 호출하는 백엔드 포 프론트엔드
5. 현 상태 유지. 터미널 UI(TUI)로 목록 조회 개선

## Decision

**옵션 1을 채택합니다.**

새 패키지 `web`을 `cli`, `api`와 동급인 세 번째 어댑터로 둡니다. 의존 대상은 `core`와 `store`이며 다른 어댑터의 모듈을 import하지 않습니다.

화면은 서버에서 HTML로 렌더링합니다. 부분 갱신이 필요한 곳에는 HTMX를 사용하며, JavaScript 빌드 툴체인(npm, 번들러)을 저장소에 도입하지 않습니다.

HTML 표현은 `Todo.Web.View`가 소유합니다. 도메인 타입에 렌더링 인스턴스를 붙이지 않습니다. `ADR-0003`이 JSON에 대해 정한 원칙과 같습니다.

`web`과 `api` 실행 파일 모두 `runSettings`와 `setHost "127.0.0.1"`로 루프백에만 바인딩합니다. `api`의 바인딩 교정은 이 결정의 일부이며, 웹 표면 없이도 단독으로 적용됩니다.

상태를 바꾸는 요청은 `Sec-Fetch-Site` 헤더가 `same-origin`인 경우에만 처리합니다. 헤더가 없는 요청도 거부합니다.

`TODO-API-v1` 계약은 바뀌지 않습니다. 라우트, 필드, 오류 코드가 그대로입니다.

## Why

**왜 세 번째 어댑터인가.** 옵션 4(웹이 API를 HTTP로 호출)는 익숙한 구조이지만 여기서는 손해입니다. 사용자가 프로세스를 둘 띄워야 하고, 실패 방식이 두 배가 되며, `ARCHITECTURE.md`의 의존 규칙 5가 금지하는 어댑터 간 참조가 됩니다. 무엇보다 얻는 것이 없습니다. `PROD-INV-003`을 지탱하는 것은 API 재사용이 아니라 `Todo.Core.UseCase` 공유이고, 직접 호출로도 그 근거가 똑같이 성립합니다. 세 표면이 모두 같은 유스케이스를 호출한다는 사실은 `scripts/quality/architecture-check.sh`가 의존 방향으로 검사합니다.

**왜 서버 렌더링인가.** 옵션 2와 3은 JavaScript 툴체인을 데려옵니다. 그 비용은 프론트엔드 코드 몇 줄이 아니라 저장소 전체에 퍼집니다. `scripts/quality/lint.sh`, `scripts/quality/test.sh`, CI, `../ai/DEFINITION_OF_DONE.md`가 전부 "fourmolu + cabal"을 전제로 쓰여 있고, 두 번째 툴체인이 들어오면 이것들이 모두 확장되어야 합니다. 이 저장소가 지키려는 것이 장기적 일관성이라면, 화면 하나를 위해 빌드 시스템을 둘로 만드는 것은 방향이 반대입니다.

**왜 CORS를 열지 않는가.** 옵션 3이 특히 나쁩니다. `api`에 CORS를 열면, 사용자가 방문한 임의의 웹페이지에서 실행되는 스크립트가 루프백 API에 요청을 보낼 수 있게 됩니다. 인증이 없으므로 그 요청은 전부 성공합니다. 서버 렌더링은 브라우저가 다른 출처로 요청을 보낼 일 자체를 만들지 않으므로 이 문제가 발생하지 않습니다.

**왜 루프백 바인딩이 결정의 일부인가.** 이것이 비목표를 옮길 수 있게 해주는 조건입니다. GUI가 위험했던 이유는 GUI 자체가 아니라 GUI가 데려오는 접근성이었습니다. "화면이 생겼으니 폰에서도 보자"는 요구는 자연스럽게 뒤따르고, 그 순간 인증 없는 API가 네트워크에 열립니다. 루프백 바인딩은 그 경로를 코드에서 막습니다. 문서에 "로컬에서만 쓰세요"라고 쓰는 것과 다른 주소로는 연결이 되지 않는 것은 다른 종류의 약속입니다.

`api`를 함께 고치는 이유는 일관성 때문만이 아닙니다. 지금까지 API는 필요할 때만 잠깐 켜는 도구였으므로 노출 시간이 짧았습니다. 화면이 생기면 사용자는 서버를 하루 종일 켜둡니다. 전제를 강제하지 않은 채 노출 시간만 늘리는 변경은 받아들일 수 없습니다.

**왜 `Sec-Fetch-Site`인가.** 폼 제출은 CORS의 제약을 받지 않습니다. 다른 출처의 페이지가 `localhost`로 상태 변경 폼을 제출할 수 있습니다. 일반적인 방어인 SameSite 쿠키는 세션이 없는 이 제품에 적용되지 않고, CSRF 토큰은 상태 저장을 요구합니다. `Sec-Fetch-Site`는 브라우저가 붙이고 페이지가 위조할 수 없으며 상태를 남기지 않습니다. 헤더가 없는 요청까지 거부하면 이 헤더를 보내지 않는 오래된 브라우저에서 웹 표면이 동작하지 않지만, 그 경우 CLI와 API가 그대로 있습니다.

**왜 TUI가 아닌가.** 옵션 5는 툴체인 문제가 전혀 없어 매력적입니다. 채택하지 않은 이유는 요청의 내용이 "터미널을 더 잘 쓰고 싶다"가 아니라 "터미널 밖에서 보고 싶다"였기 때문입니다. TUI는 같은 창 안에서 문제를 푸는 것이고, 넓은 화면과 마우스라는 요구를 만족시키지 못합니다.

## Consequences

### Positive

- GUI를 얻으면서 호스팅, 계정, 동기화를 도입하지 않습니다. 나머지 비목표가 그대로 유지됩니다.
- `PROD-INV-005`가 유지됩니다. 원격 자산을 불러오지 않으므로 데이터가 로컬 파일 밖으로 나갈 경로가 생기지 않습니다.
- 기존 `TODO-API-v1` 소비자가 영향을 받지 않습니다.
- 단일 툴체인이 유지되어 `lint.sh`, `test.sh`, CI, 완료 정의가 그대로 적용됩니다.
- `api`의 바인딩 문제가 함께 해결됩니다. 이 ADR이 없었어도 고쳐야 했던 것입니다.
- SQLite 스키마가 바뀌지 않으므로 기존 데이터베이스 파일에 마이그레이션이 필요 없습니다.

### Negative

- 표면이 셋이 되어 `PROD-INV-003`을 유지할 대상이 하나 늘었습니다. 도메인 규칙을 바꿀 때 확인할 곳이 늘어납니다.
- 서버 렌더링은 상호작용의 표현 범위가 좁습니다. 드래그 정렬 같은 조작은 어렵거나 불가능합니다.
- 브라우저를 켜 두면 데이터베이스 연결이 상시 유지됩니다. 지금까지 없던 사용 패턴입니다.
- `Sec-Fetch-Site`를 보내지 않는 오래된 브라우저에서 상태 변경이 동작하지 않습니다.
- HTMX가 새 의존성입니다. 자체 서빙하므로 원격 의존은 아니지만 학습 대상이 하나 늘었습니다.

### Risks and Mitigations

- 위험: 뷰가 도메인 규칙을 다시 계산합니다. 정렬 순서, 마감일 강조, 전이 가능 여부를 화면 코드가 판단하면 세 번째 진실이 생깁니다. 완화: 뷰는 `Todo.Core.Filter`와 `Todo.Core.Status`의 결과를 표시만 합니다. "완료 버튼을 보일지"는 뷰의 조건문이 아니라 `Todo.Core.Status.transition`이 답합니다. 이 금지를 새 패키지의 AGENTS.md에 남깁니다.
- 위험: 사용자 입력이 이스케이프 없이 HTML에 삽입됩니다. 완화: lucid의 기본 이스케이프에 의존하고 사용자 값에 `toHtmlRaw`를 쓰지 않습니다. 보안 테스트로 검증합니다.
- 위험: 편의를 위해 루프백 제약을 푸는 압력이 생깁니다. 완화: 이 ADR과 `../product/vision.md`의 비목표에 근거를 남기고, 바인딩 주소를 환경 변수로 노출하지 않습니다.
- 위험: 표면이 셋이 되었는데 동시 접근 테스트는 둘만 다룹니다. `INC-2026-001`의 교훈이 정확히 이 형태였습니다. 완화: 회귀 테스트를 세 연결로 확장합니다.
- 위험: 화면에서 목록이 길어지며 전체 조회 방식의 비용이 드러납니다. 완화: 즉시 해결하지 않고 `ADR-0001`의 재검토 조건에 도달했다는 신호로 취급합니다.

## Verification

- 아키텍처 검사: `../../scripts/quality/architecture-check.sh`. `ALLOWED`에 `web`을 `core`, `store`만 의존하도록 등록하고 `ADAPTER_PREFIX`에 `Todo.Web.`을 등록합니다. 어댑터 간 참조와 도메인 순수성이 기계적으로 검사됩니다.
- 컨텍스트 검사: `../../scripts/context/validate-context.sh`가 새 패키지의 경계 문서를 요구합니다.
- 보안 테스트: HTML 이스케이프와 `Sec-Fetch-Site` 거부 경로. 새 패키지의 테스트에 둡니다.
- 바인딩 확인: 두 서버 모두 루프백 외의 주소에서 접속되지 않아야 합니다.
- 표면 일관성: 같은 데이터베이스에 대해 CLI `list`, 웹 목록, `GET /todos`가 같은 순서로 같은 할 일을 보여줍니다.
- 계약 무변경: `../../src/api/tests/Todo/Api/ContractSpec.hs`가 수정 없이 통과합니다.

## Revisit Conditions

- 사용자가 다른 기기에서 접속하기를 원할 때. 그것은 인증, 다중 사용자, 호스팅을 동시에 여는 Level 3이며 이 ADR을 대체하는 새 결정이 필요합니다. 루프백 제약만 조용히 푸는 변경은 허용하지 않습니다.
- 서버 렌더링만으로 필요한 상호작용을 만들 수 없다는 것이 구체적인 화면에서 드러날 때. JavaScript 툴체인 도입은 그때 별도로 결정합니다.
- 목록이 커져 전체 조회가 화면에서 체감될 때. `ADR-0001`의 재검토로 이어집니다.
- 세 표면에 규칙을 복제하는 압력이 반복해서 생길 때. `core`의 유스케이스가 부족하다는 신호이며, 웹 표면이 아니라 도메인을 고쳐야 합니다.
