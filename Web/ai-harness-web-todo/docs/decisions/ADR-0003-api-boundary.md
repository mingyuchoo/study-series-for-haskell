# ADR-0003: HTTP 경계와 전송 표현

- 상태: Accepted
- 날짜: 2026-08-22
- 결정자: Todo Maintainers
- 관련 이슈: 없음
- 대체 관계: 없음

## Context

HTTP API는 스크립트가 의존하는 공개 표면입니다. 한 번 게시한 필드 이름과 오류 코드는 소비자의 코드에 박힙니다.

Haskell에서 가장 쉬운 길은 도메인 타입에 `ToJSON`/`FromJSON`을 파생해 붙이는 것입니다. 이 편의가 나중에 어떤 비용이 되는지 결정해야 합니다.

## Decision Drivers

- 라우트 목록이 실제 구현과 어긋나지 않아야 합니다.
- 도메인 리팩터링이 자동으로 계약 파손이 되지 않아야 합니다.
- 필드 이름 변경이 코드 검토에서 눈에 띄어야 합니다.
- 오류 응답의 모양이 라우트마다 다르지 않아야 합니다.

## Considered Options

1. Servant로 라우트를 타입 수준에 정의하고 전송 표현을 도메인과 분리
2. Servant를 쓰되 도메인 타입에 JSON 인스턴스를 파생해 그대로 노출
3. `wai` 또는 `scotty`로 라우트를 값 수준에서 처리

## Decision

Servant를 사용하고, 라우트 타입 `Todo.Api.Routes.TodoApi`를 라우트의 Canonical Source로 둡니다.

전송 표현은 `Todo.Api.Types`에 따로 정의하고 JSON 인스턴스를 **파생하지 않고 손으로 작성**합니다. 도메인 값과 전송 값 사이의 변환도 명시적으로 씁니다.

모든 오류 응답은 `code`와 `message` 두 필드만 갖는 하나의 모양을 사용합니다. 소비자는 HTTP 상태가 아니라 `code`로 분기합니다.

## Why

Servant를 고른 것은 핸들러 목록이 라우트 타입과 어긋나면 컴파일되지 않기 때문입니다. `scotty`에서는 경로 오타나 누락된 핸들러가 런타임까지 살아남습니다. 부수적으로, 라우트가 타입이므로 `scripts/context/generate-route-map.sh`가 소스에서 라우트 목록을 기계적으로 추출할 수 있습니다. 문서가 코드를 따라오게 되는 것이지 그 반대가 아닙니다.

도메인 타입에 인스턴스를 파생하지 않은 이유가 이 결정의 핵심입니다. 파생하면 필드 이름을 바꾸는 리팩터링이 조용히 공개 계약을 깹니다. 컴파일도 통과하고 테스트도 통과할 수 있습니다. 손으로 쓴 인스턴스는 그런 변경이 diff에 나타나게 만듭니다. 반복 코드가 늘어나는 대신, 계약 파손이 실수가 아니라 결정이 됩니다.

`code` 기반 분기를 택한 것은 HTTP 상태 코드의 종류가 적고 의미가 겹치기 때문입니다. 400 하나에 여러 원인이 모이면 소비자가 메시지 문자열을 파싱하게 되고, 그 순간 메시지 문구가 계약이 되어 버립니다.

## Consequences

### Positive

- 라우트와 핸들러의 불일치를 컴파일러가 잡습니다.
- 라우트 지도가 손으로 관리되지 않습니다.
- 도메인 구조를 계약 파손 없이 바꿀 수 있습니다.
- 오류 처리가 소비자 쪽에서 단순해집니다.

### Negative

- DTO와 변환 코드가 중복처럼 보입니다.
- Servant의 타입 수준 오류 메시지는 처음 보는 사람에게 읽기 어렵습니다.
- 필드를 추가할 때 도메인, DTO, 계약 문서, 계약 테스트 네 곳을 함께 고쳐야 합니다.

### Risks and Mitigations

- 위험: 편의를 위해 DTO를 없애고 도메인을 직접 직렬화하려는 압력이 생깁니다. 완화: 이 ADR과 `src/api/AGENTS.md`에 금지 사유를 남깁니다.
- 위험: 계약 문서와 구현이 벌어집니다. 완화: `ContractSpec`이 계약 문서의 각 약속을 검증합니다.

## Verification

- 계약 테스트: `src/api/tests/Todo/Api/ContractSpec.hs`
- 라우트 사실: `docs/generated/route-map.md`
- 사람이 읽는 계약: `../contracts/api/TODO-API-v1.md`

## Revisit Conditions

- 소비자가 늘어 클라이언트 코드 생성이 필요해질 때. Servant는 그 방향으로 확장하기 좋습니다.
- 인증을 도입할 때. 그것은 Level 3이며 별도 ADR이 필요합니다.
- DTO 변환이 명백한 기계적 반복이 되어 오류가 반복해서 생길 때.
