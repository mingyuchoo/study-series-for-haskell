# Required Impact Analysis

비사소한 변경을 구현하기 전에 아래 영역을 조사합니다. 영향이 없다고 판단한 항목은 그 이유를 설명할 수 있어야 합니다.

## Domain

- 어떤 도메인 불변조건이 영향을 받습니까? (`../domain/`)
- 상태 기계나 검증 규칙이 바뀝니까?
- 용어의 의미가 바뀝니까? (`../product/terminology.md`)

## Code

- 어떤 패키지가 영향을 받습니까?
- 규칙을 `core`에 두는 대신 어댑터에 복제하고 있지는 않습니까?
- 의존 방향이 바뀝니까? `core`가 여전히 순수합니까?
- 기존 타입과 함수를 재사용할 수 있습니까?

## Data

- SQLite 스키마가 바뀝니까? (`../contracts/data/TODO-STORE-v1.md`)
- 저장 인코딩이나 값 집합이 바뀝니까?
- 기존 데이터베이스 파일에 어떤 영향이 있습니까? 마이그레이션과 롤백이 필요합니까?
- 이전 버전의 실행 파일이 새 파일을 열면 어떻게 됩니까?

## API

- 요청, 응답, 오류 계약이 바뀝니까? (`../contracts/api/TODO-API-v1.md`)
- 필드 추가입니까, 제거나 이름 변경입니까?
- `code` 값 집합이 바뀝니까?
- 하위 호환성, 버전 관리, 폐기 절차가 필요합니까?
- `docs/generated/route-map.md`를 다시 생성해야 합니까?

## CLI

- 명령 이름, 옵션 이름, 기본값이 바뀝니까?
- 출력 형식이 바뀝니까? 이 형식에 의존하는 스크립트가 깨집니까?
- 종료 코드의 의미가 바뀝니까?

## Events

- 현재 게시된 이벤트 계약이 없습니다. 이벤트를 도입하는 변경이라면 `../contracts/events/README.md`의 안내를 먼저 확인합니다.

## Security

- 새 입력 경로가 생깁니까? 검증은 어디서 이루어집니까?
- 사용자 데이터가 로컬 파일 밖으로 나갈 가능성이 생깁니까? (`PROD-INV-005`)
- 오류 메시지가 경로, SQL, 내부 구조를 노출합니까?
- 인증이나 다중 사용자 개념이 암묵적으로 도입됩니까?

## Operations

- 동시 접근 동작이 달라집니까? (`../incidents/INC-2026-001.md`)
- 실패, 재시도, 시간 제한 동작이 달라집니까?
- 새 환경 변수나 설정이 생깁니까?
- 사용자가 기존 데이터베이스 파일로 새 버전을 실행하면 어떻게 됩니까?
