# Context Policy

## 목적

컨텍스트를 발견하고, 검증하고, 공고화하고, 폐기하는 수명 주기를 정의합니다.

## 저장할 정보

- 장기적으로 유효한 제품 목적과 불변조건
- 도메인의 의미, 규칙과 용어
- 아키텍처 결정의 배경, 대안과 트레이드오프
- 표면과 저장 형식의 공개 계약
- 반복 가능한 사고 교훈과 알려진 실패 방식
- 실행 가능하거나 기계적으로 생성되는 현재 사실

## 저장하지 않을 정보

- 확인되지 않은 추측
- 작업 중간의 사고 과정
- 이미 Canonical Source에 있는 내용의 복제본
- 코드가 이미 강제하는 사실을 문장으로 옮긴 것
- 개인 환경의 비밀값이나 자격 증명
- 사용자의 실제 할 일 데이터
- 제거 조건과 책임자가 없는 임시 예외
- 대화 기록만으로 만들어진 사실

특히 두 번째와 네 번째가 이 저장소에서 자주 어긋납니다. 예를 들어 상태 전이 표를 도메인 문서와 서비스 문서와 계약 문서에 모두 적으면 셋이 갈라집니다. 규칙은 `Todo.Core.Status`와 그 테스트에 두고, 문서는 그것을 가리키며 왜 그렇게 정했는지를 씁니다.

## 계층적 검색

컨텍스트는 다음 순서로 좁혀 검색합니다.

1. 전역: `INDEX.md`, `../../ARCHITECTURE.md`
2. 영역: 제품, 도메인, ADR, 계약, 사고 기록
3. 지역: 패키지의 `AGENTS.md`, `CLAUDE.md`, `docs`
4. 작업: 활성 계획, 관련 코드와 테스트

## 공고화

작업 중 발견한 지식은 미래에도 반복해서 필요하고 검증 가능한 경우에만 다음 중 적절한 형태로 승격합니다.

| 지식의 종류 | 승격 대상 |
|---|---|
| 도메인 불변조건 | `core`의 테스트 |
| 경계 규칙 | `scripts/quality/architecture-check.sh` |
| 표면 간 약속 | `../contracts` + 계약 테스트 |
| 중요한 선택의 이유 | ADR |
| 비즈니스 의미 | 도메인 문서 |
| 현재 구조의 사실 | 생성기와 `../generated` |
| 탐색 절차 | 에이전트 지침 |

가능하면 문서보다 실행 가능한 형태를 고릅니다. 테스트는 어긋나면 실패하지만 문서는 조용히 낡습니다.

## Garbage Collection

다음 신호를 지속적으로 검사합니다.

- 깨진 문서 링크와 고아 문서
- 폐기된 결정을 가리키는 지침
- 구현과 다른 계약 또는 생성 문서
- 중복되거나 충돌하는 에이전트 지침
- 만료된 임시 예외
- 끝났지만 활성 상태인 실행 계획

정기 검사와 Pull Request 검사는 `../../scripts/context`와 Context Integrity CI가 담당합니다.
