# API Contract: Todo API

- 상태: Active
- 소유 패키지: api
- 소비자: 로컬 사용자 도구, 스크립트
- 버전: v1

## Purpose

할 일의 생성, 조회, 수정, 상태 변경과 삭제를 HTTP로 제공합니다. `cli`, `web`과 같은 유스케이스를 호출하므로 모든 표면의 규칙이 같습니다.

## Authentication and Authorization

없습니다. 인증이 없으므로 접근 경로 제한이 유일한 방어선입니다.

서버는 `127.0.0.1`에만 바인딩합니다. 이는 운영자가 지켜야 할 전제가 아니라 실행 파일이 강제하는 제약이며, 수신 주소를 바꾸는 설정을 제공하지 않습니다. 근거는 `../../decisions/ADR-0004-web-surface.md`에 있습니다.

같은 기계의 다른 프로세스는 이 API에 접근할 수 있습니다. 이 API가 방어하는 것은 네트워크 노출이지 로컬 프로세스가 아닙니다.

인증이나 다중 사용자 개념을 도입하는 변경, 그리고 루프백 밖으로 바인딩을 여는 변경은 Level 3이며 ADR과 사람의 승인이 필요합니다.

## Resources

라우트의 기계적 사실은 `../../generated/route-map.md`에 있습니다. 의미는 다음과 같습니다.

| 작업 | 의미 |
|---|---|
| `GET /todos` | 조건에 맞는 할 일을 마감일 순으로 반환합니다. 조건이 없으면 전체입니다 |
| `POST /todos` | 할 일을 만듭니다. 항상 `pending` 상태로 시작합니다 |
| `GET /todos/{todoId}` | 할 일 하나를 반환합니다 |
| `PATCH /todos/{todoId}` | 내용을 부분 수정합니다. 상태는 바꾸지 않습니다 |
| `PUT /todos/{todoId}/status` | 상태를 변경합니다 |
| `DELETE /todos/{todoId}` | 영구 삭제합니다 |

상태를 `PATCH`가 아니라 별도 자원으로 분리한 이유는 상태 변경만 상태 기계 규칙을 거치기 때문입니다. 두 관심사를 한 요청에 섞으면 부분 성공을 표현할 수 없습니다.

## Request

### 할 일 표현

| 필드 | 타입 | 필수 | 의미 |
|---|---|---|---|
| `id` | 정수 | 응답에만 | 저장소가 부여한 식별자 |
| `title` | 문자열 | 예 | 정규화된 제목. 최대 200자 |
| `list` | 문자열 | 아니오 | 목록 이름. 생략하면 `inbox` |
| `status` | 문자열 | 응답에만 | `pending`, `in_progress`, `done`, `archived` |
| `priority` | 문자열 | 아니오 | `low`, `normal`, `high`, `urgent`. 생략하면 `normal` |
| `tags` | 문자열 배열 | 아니오 | 소문자로 정규화됨. 최대 16개, 각 32자 |
| `dueOn` | 날짜 또는 null | 아니오 | `YYYY-MM-DD`. 과거 날짜는 거부 |
| `createdAt` | 시각 | 응답에만 | UTC ISO 8601 |
| `updatedAt` | 시각 | 응답에만 | UTC ISO 8601 |

### PATCH의 세 가지 경우

`PATCH /todos/{todoId}`에서 `dueOn`은 다음을 구분합니다.

| 본문 | 결과 |
|---|---|
| 필드 없음 | 마감일을 바꾸지 않습니다 |
| `"dueOn": null` | 마감일을 제거합니다 |
| `"dueOn": "2026-09-01"` | 마감일을 그 값으로 바꿉니다 |

### 질의 매개변수

`GET /todos`는 `status`, `tag`, `list`를 지원하며 모두 논리곱으로 결합합니다.

## Response

| 작업 | 성공 상태 | 본문 |
|---|---|---|
| 조회 목록 | 200 | 할 일 표현의 배열 |
| 생성 | 201 | 만들어진 할 일 표현 |
| 조회, 수정, 상태 변경 | 200 | 할 일 표현 |
| 삭제 | 204 | 없음 |

## Errors

모든 오류 응답의 본문은 `code`와 `message` 두 필드만 가집니다.

| `code` | HTTP | 원인 | 재시도 |
|---|---|---|---|
| `invalid_request` | 400 | 값 검증 실패, 인식할 수 없는 열거값 | 요청을 고친 뒤에만 |
| `not_found` | 404 | 존재하지 않는 식별자 | 아니오 |
| `invalid_transition` | 409 | 상태 기계가 허용하지 않는 전이 | 아니오 |

경로 매개변수의 형식 오류는 Servant가 400으로 처리하며 본문 형식이 위와 다릅니다.

소비자는 HTTP 상태가 아니라 `code`로 분기합니다. 상태 코드는 전송 계층의 신호이고 `code`가 안정적인 약속입니다.

## Idempotency and Retry

- `PUT /todos/{todoId}/status`는 멱등입니다. 이미 목표 상태이면 아무것도 바꾸지 않고 200과 현재 표현을 반환합니다. `updatedAt`도 바뀌지 않습니다.
- `DELETE`는 첫 요청에 204, 이후 요청에 404입니다. 이미 없는 자원을 성공으로 위장하지 않기 위한 선택입니다.
- `POST /todos`는 멱등이 아닙니다. 같은 본문을 두 번 보내면 두 개가 만들어집니다. 멱등 생성이 필요해지면 멱등성 키를 도입하고 버전을 올립니다.

## Compatibility

- 응답에 필드를 추가하는 것은 호환 변경입니다. 소비자는 모르는 필드를 무시해야 합니다.
- 필드 제거, 이름 변경, 타입 변경, `code` 값 제거는 호환을 깨는 변경이며 `v2` 경로와 폐기 기간이 필요합니다.
- `status`와 `priority`의 값 집합에 값을 추가하는 것은 소비자가 알 수 없는 값을 만나게 하므로 부가 호환 변경으로 취급하고 계약을 먼저 갱신합니다.
