# INC-2026-001: 동시 쓰기 중 CLI 명령이 데이터베이스 잠금으로 실패

- 상태: Example
- 발생 시각: 2026-07-14 09:12 KST
- 복구 시각: 2026-07-14 09:41 KST
- 심각도: 중간
- 책임자: store 담당

이 문서는 사고 기록의 작성 예시입니다. 자세한 설명은 `INDEX.md`에 있습니다.

## Summary

`api`를 배경에서 실행해 두고 스크립트가 주기적으로 할 일을 추가하는 상태에서, 사용자가 `cli done`을 실행하면 `SQLITE_BUSY: database is locked` 오류로 명령이 실패했습니다. 데이터가 손상되지는 않았지만 사용자가 상태를 바꿀 수 없었습니다.

## Impact

- 영향 받은 기능: 쓰기를 수행하는 모든 CLI 명령
- 영향 받은 사용자: HTTP API를 함께 사용하는 사용자
- 기간: 29분
- 데이터 손실: 없음. 실패한 명령은 저장소를 전혀 바꾸지 않았습니다

## Detection

사용자가 직접 발견했습니다. 이 앱은 로컬 도구이므로 서버 측 경보가 없고, 단일 표면만 쓰는 개발 환경에서는 재현되지 않았습니다. 두 표면을 동시에 실행하는 테스트가 없었던 것이 더 일찍 탐지하지 못한 이유입니다.

## Root Cause

직접 원인은 SQLite의 기본 저널 모드가 `delete`이고 busy timeout이 0이라는 점입니다. 이 조합에서는 다른 연결이 쓰기 잠금을 잡고 있으면 대기 없이 즉시 실패합니다.

이를 가능하게 한 시스템 조건은 다음과 같습니다.

1. 제품이 CLI와 HTTP API 두 표면을 제공하고 둘이 같은 파일을 쓰도록 설계되었는데, 연결 설정이 단일 프로세스 사용을 전제하고 있었습니다.
2. 데이터베이스 연결 설정이 어디에도 문서화되어 있지 않아 전제가 검토된 적이 없었습니다.
3. 테스트가 모두 단일 연결을 사용했습니다.

## Resolution and Recovery

`Todo.Store.Migration.configureConnection`에서 연결마다 다음을 설정했습니다.

- `PRAGMA journal_mode = WAL`: 읽기와 쓰기가 서로를 막지 않습니다.
- `PRAGMA busy_timeout = 5000`: 짧은 경합에서 즉시 실패하지 않고 대기합니다.

데이터 정합성은 별도 조치가 필요 없었습니다. 실패한 트랜잭션은 시작되지 않았기 때문입니다.

## What Went Well

- 실패가 조용하지 않았습니다. 오류가 명확했고 부분 저장이 없었습니다.
- 트랜잭션 경계 덕분에 정합성 확인 작업이 필요 없었습니다.

## What Did Not Go Well

- 두 표면 동시 사용이 제품 설계의 일부인데 테스트가 그 상황을 전혀 다루지 않았습니다.
- 연결 설정이라는 중요한 운영 결정이 코드에만 있고 문서에 없었습니다.

두 번째와 세 번째 행이 이 사고의 성격을 보여줍니다. 2026-07-14의 조치는 옳았지만 **적용 순서가 틀려 있었고**, 정상 상태의 쓰기만 테스트했기 때문에 오래 드러나지 않았습니다. 경합은 쓸 때만이 아니라 **열 때도** 일어납니다.

세 번째 행은 한 걸음 더 나갑니다. 순서를 고친 뒤에도 실패가 남았고, 원인은 **`busy_timeout`이 만능이 아니라는 점**이었습니다. 저널 모드 전환은 배타적 잠금을 요구하면서도 busy handler를 거치지 않습니다. 설정 하나로 동시성 문제가 해결되었다고 믿은 것이 이 사고가 세 번 반복된 이유입니다.

세 번 모두 같은 구조였습니다. **제품이 약속한 사용 방식(여러 표면이 한 파일을 공유)을 그 방식대로 실행해 보지 않은 것.** 세 번째는 사용자가 `run.sh web --with-api`를 실제로 실행하면서 드러났습니다.

이 사고가 남긴 것은 조치 세 가지가 아니라 규칙 하나입니다. **표면을 늘리는 변경은 그 표면을 함께 실행하는 테스트를 함께 늘립니다.** 위 표는 그 규칙이 실제로 적용된 기록이며, 다음 표면이 생기면 행이 하나 더 늘어야 합니다.
